## 逐步审阅

### 第一步：确认地图职责（约 10 分钟）

先读地图的“职责与采样”“工具输入与查询方式”和“返回信息”。地图采用有界概览加当前窗口，每次调用重新采样，不保留旧地图分页或跨调用地图缓存，也不引入独立 freshness 机制。审阅重点是地图最小需要哪些信息；标准地图不含保护/savings 政策。字段正式命名和输出限额由实现方收敛。

建议反馈：`地图职责同意；必须保留……；可以删去/推迟……。`

### 第二步：采样技术核对（由实现方负责，无需用户逐项审阅）

Query 提案已经记录 store 准备路径、meter 对齐、cut、租约和 TS 只读约束。实现方按提案落实正式类型；只有会改变使用方式或增加明显成本的取舍才带回审阅。运行时序及发布兼容性仍须在实施阶段测试，不能用源码调查代替。

用户可以跳过 Query 的内部实现细节，直接继续审阅主动压缩的使用行为。

### 第三步：确认主动压缩行为（分两次，各约 15 分钟）

1. 先看输入、保护和多区间执行的使用行为。薄 provider 已由源码调查收敛，不再要求用户判断导入/hook 可行性；重点看最近任务来源及摘要应保留哪些信息。tail→head、首个失败停止、不回滚作为实施方案，不反复抬成技术问卷。
2. 再看独立顶层准入、全成功隐藏和验收。确认 native/both、仅拒压缩不取消 siblings、partial/错误/取消保留原 pair，以及隐藏前中断不加恢复队列。

建议反馈：`我的任务还来自……；摘要必须保留……；压缩行为上还担心……。`

### 第四步：校准提醒与预算（约 15–20 分钟）

用户只需确认优先支持哪些工作路由，以及提醒是否应为一次普通地图/回读准备留出空间。实现方负责取得容量、输出预留和原生配置，提出 S/R、notice 与摘要批次预算，并用样例及实际成本校准；不要求用户自行计算阈值或逐项选择内部参数。

建议反馈：`优先支持路由……；提醒应留出一次地图/回读准备；其他使用偏好是……。`

这些时间仅估计阅读与判断，不包括源码调查或实际路由成本实验。每轮只改该轮拥有的决策；关联变化用链接跟进，不在四份里重复维护同一细节。

## 实施顺序与验收

1. Query capture 与地图：落实既定 store 准备路径与同步只读采样，验证 live/cold、返回 DTO 所有权和当前窗口查询。
2. 提交及隐藏：至少双非相邻区间，覆盖 partial、取消、准入、最终结算和 replay。
3. 提醒：验证隐藏→原生 pressure→重测→本次 notice 的真实 Loader 时序，逐路由校准预算。
4. 连续工作与成本评测：测试压缩后继续完成任务，记录实际 usage、额外请求、缓存和延迟；首版完成必须覆盖上述三项能力。

实施任务以四份决策记录为依据；待校准值需用运行证据确定。优先用现有 testkit、Mock LLM、keyless session snapshot 和真实 Loader 组合，不新增测试框架。

## 设计资料归属

| 主题 | 权威设计记录 |
|---|---|
| 地图职责、当前窗口、计量依据与输出预算 | 通用地图 ADR 0004 |
| live/cold 同步采样、TS 只读原 Session、内部 meter 适配、cut 与租约 | Query 同步采样提案 |
| 多区间提交、目标检查、保护、独立调用、结算与工具对清理 | 主动压缩 ADR 0001 |
| 提醒时序、压力阈值、预算、原始 Log 状态恢复与原生兜底 | 提前提醒 ADR 0002 |

技术证据及必要限制随对应记录维护。Query 只读接口隐藏写入方法，运行时仍传原始完整 Session；session-tools 内部断言后调用未修改的 meter。地图按需采样当前窗口；ACP 按所选目标检查，不以全局 generation 变化一律拒绝。能力限制见各记录，不增加旧正文缓存。

提醒复位只更新内存，不新增 reset 事件或修改核心 append API。恢复时当前 T < R 直接恢复资格，否则查原始 Log：有 ACP 提醒则延续已提醒状态，无提醒则允许提醒。仅排除“降压后再升高、第二条提醒落档前恰好重启”的窗口；压力骤增不作特殊处理，保留原生兜底。
